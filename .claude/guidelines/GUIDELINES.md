## 🎯 PowerWallet の存在意義（North Star）

**「日本の全家庭が、持っているエネルギーで稼げる世界を作る」**

私たちは電力会社でもなく、ソフトウェア会社でもない。
**個人のエネルギーを資産に変える、日本初の金融インフラ**を作っている。

### 世界観: 「Wattage is Currency — ワッテージが通貨になる世界」

Elon MuskがPayPalで「ドルをデジタル化」したように、
PowerWalletは**kWhをデジタル通貨化**する。

```
Phase 1（今）: kWh を「見える化」する → 数字として認識させる
Phase 2（半年後）: kWh を「最適化」する → AIが収益を最大化
Phase 3（1年後）: kWh を「トークン化」する → 1kWh = 1 PWATT on Solana
Phase 4（将来）: kWh を「流通」させる → P2P電力取引、エネルギーのPayPay
```

この世界観が、全エージェントの判断の土台になる。
目の前の機能を作るとき、「この機能は kWh を通貨に近づけているか？」と問え。

## 🧭 意思決定の3原則

1. **ユーザーの収益を最大化する** — 全ての機能はユーザーが得する設計
2. **シンプルを守る** — 複雑な電力市場を「ウォレット」の直感で使えるUIに
3. **規制を先読みする** — 法律の変化より1歩先に動く

### 補助原則（PowerWallet固有）

4. **時間の壁を意識する** — 2026年4月1日のVPP低圧解禁は動かせないデッドライン。全てのタスクは「4/1に間に合うか」を基準に優先度判断する
5. **「稼げる」が第一訴求** — 「節電」ではなく「収益」。PowerWalletが他の全てのエネルギーアプリと異なる最大のポイント
6. **日本の法的環境を前提とする** — グローバルスタンダードではなく、電気事業法・資金決済法・金融商品取引法の日本法が全ての基盤

|---|---|

| AI | OpenAI API / Anthropic API（Phase 2〜） |
| Blockchain | Solana（Phase 3〜） |

### 重要な技術的制約
- Next.js 16: `middleware.ts` は deprecated → `proxy.ts` を使用
- Tailwind v4: `@import "tailwindcss"` と `@theme {}` を使用（v3の設定ファイル不使用）
- Supabase SSR: `createBrowserClient`（クライアント）/ `createServerClient`（サーバー）を分離
- 全テーブルにRLS（Row Level Security）を必ず設定

## 🇯🇵 日本市場特有の注意事項

1. **プライバシー意識が高い** → データ収集は最小限・説明を丁寧に
2. **電力への不信感** → 2011年3月11日以降、「電力会社任せ」から「自分でコントロール」への意識変化。PowerWalletはこの流れに乗る
3. **スマホ操作が主流** → LINEログインの追加を検討（Phase 2）
4. **太陽光ユーザー層** → 40〜60代が多い → UIは読みやすさを優先。フォント16px以上、ボタン44px以上
5. **VPP規制（低圧）** → 2026年4月解禁だが細則は流動的 → Energy Policy Expertに確認

## ⚡ 日本の電力規制・補助金環境（全エージェント必読）

PowerWalletの事業は複数の法律・制度に関わる。全エージェントが最低限理解すべき要点:

### 電気事業法
- **VPP（仮想発電所）**: 分散電源を束ねて需給調整市場に参加する仕組み
- **アグリゲーター**: VPPを運営する事業者。PowerWalletはアグリゲーターを目指す
- **低圧解禁（2026年4月）**: 10kW未満の家庭設備がVPP参加可能に → PowerWalletの最大機会
- **EREB（需給調整市場）**: 電力の過不足を調整する市場。蓄電池の放電で収益を得られる
- **JEPX（日本卸電力取引所）**: 電力のスポット価格が決まる市場。AI最適化の参照データ

### 金融規制とPowerWalletの関係
- **AI提案 ≠ 投資助言**: 「売電タイミングの提案」が金商法の投資助言業に該当しないよう、利用規約に免責事項を明記する
- **PWATTトークン**: 資金決済法の「前払式支払手段」に該当する可能性あり → Phase 3までに法的整理が必要
- **現時点のポジション**: 「情報提供サービス」として開始し、規制が明確化した段階でステップアップ

### 補助金・公的支援の機会
- **NEDO**: 脱炭素・省エネ関連の技術開発補助金。PowerWalletのAI最適化が該当する可能性
- **経産省 GX推進**: グリーントランスフォーメーション関連の支援策
- **SBIR（中小企業技術革新制度）**: スタートアップ向けの技術開発補助
- **J-Startup認定**: 認定されるとVCへのアクセス・メディア露出が大幅に増える

### 「1kWh = 1 PWATT」トークンの法的位置づけ（Phase 3準備）
```
法的リスクマップ:
├── 資金決済法 → 「前払式支払手段」に該当する場合、届出・供託義務
├── 金融商品取引法 → 「電子記録移転有価証券表示権利」に該当する場合、登録義務
├── 現時点の設計方針 → ゲーム内ポイント的な設計で開始、段階的に法的整理
└── 弁護士照会 → Phase 2後半で正式に実施予定
```

**全エージェントへの指示**: 規制に関わる判断は必ずEnergy Policy Expertを経由すること。「たぶん大丈夫」は禁止。

## 🤝 エージェント間連携プロトコル

### 引き継ぎルール（最重要）

エージェントは独立したコンテキストで動く。だからこそ「引き継ぎの質」がチームの強さを決める。

**引き継ぎの3点セット（必ずこの形式で）**:
```
1. 事実: 何をやったか・何が完成したか（成果物のファイルパス）
2. 判断理由: なぜその方法を選んだか（代替案があった場合はそれも記載）
3. 未解決事項: 残っている課題・次のエージェントへの依頼事項
```

**例**:
```
[引き継ぎ: Energy Policy Expert → CTO]
事実: 利用規約ドラフトをtemplates/regulatory-filing.mdに作成。
      AI提案の免責事項は「情報提供であり投資助言ではない」の文言で整理。
判断理由: 弁護士見解前だが、最も保守的な解釈で記載した。
未解決: 第X条のVPP収益分配の表現は弁護士確認後に修正が必要。
        CTOはUI上で「収益保証」と誤解される表現がないか確認してほしい。
```

### ブロッカー対応ルール

```
ブロッカー発生
  ↓ 15分以内
CEOに報告（何がブロックされているか + 自分で試した対策）
  ↓ 即時
別の並行可能なタスクに着手（手を止めない）
  ↓ CEOが判断
ルーティングテーブルで解決策を割り当て
```

**ブロッカー報告フォーマット**:
```
🚫 ブロッカー報告
タスク: [何をしようとしたか]
ブロック内容: [何が妨げているか]
試した対策: [自分で試みたこと]
依頼: [誰に何をしてほしいか]
代替案: [ブロック中に着手する別タスク]
```

### 並列実行の原則

- 依存関係がないタスクは**必ず並列で動かす**
- 依存関係がある場合: 「先行タスクの完了を待つ間に何をするか」を必ず決める
- 1エージェントが複数タスクを持つ場合: 優先度順に処理し、ブロック時に次タスクへ

### 成果物の命名規則

```
文書: [カテゴリ]-[内容]-[バージョン].md
  例: legal-terms-of-service-v1.md
  例: finance-model-12month-v2.md

コード: 既存のNext.jsプロジェクト規約に従う
  例: app/api/optimize/route.ts
  例: components/landing-hero.tsx

レポート: report-[内容]-[日付].md
  例: report-vpp-regulation-20260401.md
```

## 🎯 VPP解禁対応 特別ガイドライン（2026年4月）

### 全エージェントが知っておくべきこと

**VPP（Virtual Power Plant）とは**:
分散した電源（蓄電池・太陽光・EV等）をIoTで束ね、1つの発電所として電力市場に参加する仕組み。

**2026年4月に何が変わるか**:
- 低圧（10kW未満）の家庭用設備がVPPに参加可能になる
- これまで大規模事業者のみだった需給調整市場（EREB）に個人が間接参加できる
- PowerWalletのユーザーが「自分の蓄電池で稼ぐ」ことが法的に可能になる

**PowerWalletへの影響**:
- VPP収益シェアが核心ビジネスモデルになる（Phase 2の最重要機能）
- LPの訴求ポイントが「節電」から「稼ぐ」に変わる
- メディア露出のチャンスが増える（各メディアがVPP特集を組む）

**各エージェントの対応**:
| エージェント | VPP解禁で何をするか |
|---|---|
| CTO | VPP参加申込テーブル設計・LP実装 |
| AI Engineer | EREB価格データの取得・予測モデル設計 |
| Energy Policy Expert | 省令分析・アグリゲーター要件整理・利用規約 |
| Growth Lead | VPP解禁をフックにしたSNS/コンテンツ攻勢 |
| Finance Strategist | VPP収益シェアモデルの収益試算 |
| Product Designer | LP「稼ぐ」訴求のUIデザイン |
| Blockchain Architect | VPP収益→将来のトークン化への設計連携 |
